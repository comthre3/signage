# AI Menu Import — Design Spec

**Date:** 2026-09-08
**Status:** Approved in conversation (nine design sections); awaiting written-spec review
**Supersedes:** the "Phase 3 preview / early access" promise on the landing page (`features.ai.*`, `spotlight.*`)
**Implementation:** two plans — Plan A (Menus core) then Plan B (AI import) — see §12

## 1. Goal

Let a shop owner turn their existing menu into polished, bilingual signage in minutes:
paste a website URL or upload a menu PDF/photos → Khanshoof extracts the menu, brand
colours and logo → the owner reviews and edits → boards are rendered to images and dropped
into a drafted playlist. Afterwards a price change is a form edit plus a re-render, not a
designer job.

**Non-goals (v1):** Instagram ingestion (blocked by Instagram; users upload a screenshot
instead), video boards, per-item photos generated by AI, automatic assignment to screens,
a public template marketplace.

## 2. Product shape

A **Menu** becomes a first-class content type beside Media and Playlists. It holds the
brand, the categories and items in English and Arabic, and a chosen template. Menu
**boards** are rendered *from* the menu data into ordinary images in the Media library, so
zones, playlists, schedules, offline caching and walls all work unchanged. The AI importer
is one way to create a Menu; a blank one can also be created by hand.

Two consequences follow:
- Editing and re-rendering are unlimited and free; only AI extraction is metered.
- The player is untouched. Boards are `image/png` media items like any upload.

## 3. Data model

New tables in `backend/db.py`, created with the existing `CREATE TABLE IF NOT EXISTS`
pattern. All rows are organisation-scoped via `organization_id` or their parent.

| Table | Columns (beyond `id`, timestamps) |
|---|---|
| `menus` | `organization_id`, `name`, `brand` JSON, `template` TEXT, `source` JSON, `last_rendered_at` |
| `menu_categories` | `menu_id`, `name_en`, `name_ar`, `sort_order` |
| `menu_items` | `category_id`, `name_en`, `name_ar`, `description_en`, `description_ar` (nullable), `price NUMERIC(10,3)` (nullable), `price_note` (e.g. "per 100 ml"), `badges` JSON (`new`, `spicy`, `vegan`, `halal`, `popular`), `is_available BOOL DEFAULT true`, `sort_order` |
| `menu_renders` | `menu_id`, `kind` (`board` \| `category` \| `promo`), `category_id` (nullable; set for `category`), `item_id` (nullable; set for `promo`), `language` (`en` \| `ar` \| `bi`), `aspect` (`16:9` \| `9:16`), `status` (`pending` \| `ready` \| `failed`), `media_id` → `media` (set when `ready`), `render_hash`, `error`, `created_at` |
| `menu_imports` | `organization_id`, `menu_id` (nullable until review), `status`, `step`, `source` JSON, `error` JSON, `usage` JSON, `created_by`, `created_at`, `finished_at` |

`brand` JSON: `{ "name_en", "name_ar", "tagline_en", "tagline_ar", "primary", "accent", "background", "logo_media_id", "currency": "KWD" }`. Colours are `#RRGGBB`.

`source` JSON: `{ "type": "url", "url": "…" }` or `{ "type": "media", "media_ids": [ … ] }`.

`menu_imports.status` state machine: `queued → fetching → extracting → review → done`,
with `failed` reachable from `fetching`/`extracting`. `review` means a Menu exists and is
waiting for the user; `done` is set when the user first saves or renders it.

`render_hash` = SHA-256 of the canonical menu JSON + template id + language + aspect +
template version. A render request skips any board whose hash already exists.

## 4. Renderer service

New compose service `renderer/`, built on the official Playwright Chromium image
(`mcr.microsoft.com/playwright`, version pinned in the Dockerfile by Plan A to the
current release at implementation time and bumped deliberately thereafter), exposing a
minimal HTTP API on the internal network only (no host port):

- `POST /render` `{ html, width, height, scale }` → `image/png`. Loads the HTML from a
  string (no network except the bundled font files), waits for fonts, screenshots the
  viewport.
- `POST /screenshot` `{ url }` → `{ png (base64), final_url, title }`. Full-page,
  1280 px wide, capped at 8 000 px tall, JavaScript on, downloads and dialogs blocked,
  20 s budget.

Both endpoints require the `X-Renderer-Token` header matching `RENDERER_TOKEN` (shared
env var between backend and renderer). Concurrency is limited to 2 in-flight renders with
a FIFO queue; further requests wait, and a request older than 60 s is rejected with 503 so
the backend can surface a retry. Fonts are baked into the image: Inter, IBM Plex Sans
Arabic, JetBrains Mono. Google Fonts is never contacted at render time.

The screenshot endpoint applies the same SSRF policy as the backend fetch (§6.1) *again*
inside the container, because the browser follows redirects on its own.

## 5. Templates

Templates are Jinja2 HTML files under `backend/menu_templates/<id>/` with a `template.json`
manifest (`id`, `name_en`, `name_ar`, `version`, supported aspects, preview thumbnail).
Each renders one of three **kinds** from the same menu data:

- `board` — the whole menu on one screen (two or three columns depending on item count),
  header with brand name/logo/tagline, footer note ("Prices in KD · halal").
- `category` — one category per board, larger type, for multi-board playlists.
- `promo` — one board per featured item, for rotating side zones. An item is featured
  when it carries the `new` or `popular` badge; at most 3 promo boards are produced per
  render, in menu order. A menu with no featured items produces no promo boards and the
  UI says so.

Languages: `en`, `ar` (full RTL with `dir="rtl"`), `bi` (English with Arabic beneath each
line). Aspects: `16:9` (1920×1080) and `9:16` (1080×1920). Launch templates:

| id | Look | Reference |
|---|---|---|
| `dark-classic` | slate board, warm accent, dotted leaders | FORNO board on the landing page |
| `cream-cafe` | cream board, brown type, rule under category | Bagel & Co. panel |
| `luxe` | black/aubergine, gold accent, thin serif-feel weights | Maison Noor totem |

Template CSS uses the brand's `primary`/`accent`/`background` as CSS variables; the
template picker shows each template already tinted with the menu's brand.

Boards render text only from the menu data plus the logo. They never embed remote images
(no hotlinking the customer's site), which keeps renders deterministic and offline-safe.

## 6. Import pipeline

Runs as an in-process `asyncio` task started by the import endpoint (same pattern as the
reminder loop). The dashboard polls `GET /menus/imports/{id}` every 2 s. Restarting the
backend loses in-flight tasks: on startup any import still in `queued`/`fetching`/
`extracting` older than 10 minutes is marked `failed` with `error.code = "interrupted"`
and does not count against quota.

### 6.1 Fetch

- **URL source.** Validate scheme is `http`/`https`; resolve the host and reject private,
  loopback, link-local and metadata ranges (10/8, 172.16/12, 192.168/16, 127/8,
  169.254/16, ::1, fc00::/7) — re-checked on every redirect (max 3). GET with a 15 s
  timeout and a 5 MB cap, a Khanshoof user-agent, `Accept-Language: en,ar`. From the HTML
  extract: readable text (scripts/styles/nav stripped, headings and price-like tokens
  kept), `<meta name="theme-color">`, `og:image`, `link rel="icon"`, and up to 6 linked
  PDFs or images whose URL or alt text mentions `menu`/`قائمة`. Then ask the renderer for
  a full-page screenshot. Linked menu PDFs (≤ 2, ≤ 10 MB each) are downloaded and
  rasterised like uploads.
- **Media source.** `media_ids` must belong to the org and be `application/pdf` or
  `image/*`. PDFs are rasterised with the existing `pdf_render.rasterize_pdf` at 1568 px
  wide, first 6 pages. Images are downscaled to a 1568 px long edge. At most 8 images total
  go to the model.

Fetch failures (unreachable, 403/429 from bot protection, non-HTML, empty text and no
images) end the import as `failed` with a code the UI maps to advice — "This site blocked
us; upload a PDF or a photo of the menu instead."

### 6.2 Extract

One request to the Anthropic API from the backend (Python SDK, `anthropic` added to
`requirements.txt`):

- Model `claude-opus-5`, adaptive thinking, `output_config.effort = "high"`, streaming
  with `get_final_message()`, server-side refusal fallbacks enabled.
- Structured output via `client.messages.parse` against a Pydantic `MenuExtraction`
  model. Every string field that reaches the UI is present in both `_en` and `_ar`;
  the model translates whatever the source lacks.
- Inputs, in this order: a frozen system prompt (cacheable), the page text, the
  screenshot, then menu page images; finally the user-facing instruction. The prompt
  asks for prices as decimals in the detected currency, `currency` reported separately,
  a `suggested_template` from the three ids, a `logo_candidate` chosen from the
  discovered image URLs (or null), and a `warnings[]` list in plain English + Arabic.
- Non-KWD prices are stored as extracted and the menu is flagged
  `brand.currency != "KWD"`; the UI shows a banner and the boards print the source
  currency. No automatic FX conversion.
- Errors: rate-limit/overloaded/5xx → 2 retries with backoff, then `failed`
  (`error.code = "ai_unavailable"`, not counted). A `refusal` stop reason after the
  fallback → `failed` (`"ai_refused"`, not counted). Token usage is stored in
  `menu_imports.usage` with a computed cost estimate.
- The logo, if a candidate URL is chosen, is downloaded (same SSRF rules, ≤ 2 MB,
  image only), stored as a media item and referenced by `brand.logo_media_id`.

`MenuExtraction` (abridged):

```
brand: { name_en, name_ar, tagline_en?, tagline_ar?, primary, accent, background, logo_candidate?, currency }
categories: [ { name_en, name_ar, items: [ { name_en, name_ar, description_en?, description_ar?, price?, price_note?, badges[] } ] } ]
suggested_template: "dark-classic" | "cream-cafe" | "luxe"
warnings: [ { en, ar } ]
```

### 6.3 Review

The import moves to `review`, the Menu rows are written, and the dashboard opens the
editor. Nothing is rendered until the user chooses to. A menu with zero items is still
created (with a warning) so the owner can type it in rather than start over.

### 6.4 Render

`POST /menus/{id}/render` accepts `{ languages, aspects, kinds }` (defaults: `["en","ar"]`,
`["16:9"]`, `["board"]`), computes the boards to produce, skips unchanged hashes, and
runs the rest through the renderer sequentially. Each PNG is written to `UPLOAD_DIR`
with a UUID filename and inserted as a `media` row named like `FORNO — Menu (EN, 16:9)`
or `FORNO — Classics (AR)`. Superseded renders keep their media rows (they may be in
playlists) but are no longer listed as current.

`POST /menus/{id}/playlist` creates — or updates, if one was created before — a playlist
named `Menu — <name>` containing the current boards at 10 s each, in category order,
English first then Arabic. Assigning it to a screen or zone uses the existing UI.

## 7. API

All endpoints use the existing auth dependencies (`require_api_scope("api:rw", …)` with
session roles `admin`/`editor` for writes, `api:ro`/any role for reads) and
`require_active_subscription`. Errors use the existing `http_error(status, code, message)`
shape.

| Method & path | Notes |
|---|---|
| `GET /ai/capabilities` | `{ "menu_import": bool }` — false when `ANTHROPIC_API_KEY` or `RENDERER_URL` is unset; the dashboard hides the feature (same pattern as `/auth/providers`) |
| `GET /ai/quota` | `{ used, limit, resets_at }` for the calling org |
| `POST /menus/import` | body = `source`; 202 `{ import_id }`; 402 `ai.quota_exceeded` when the month's limit is reached; 400 `ai.bad_source` |
| `GET /menus/imports/{id}` | `{ status, step, error, menu_id, created_at }` |
| `GET /menus` | list with item counts and `last_rendered_at` |
| `POST /menus` | create a blank menu `{ name, template }` |
| `GET /menus/{id}` | full tree: brand, categories, items, current renders |
| `PUT /menus/{id}` | full replace of brand + tree (validated; ids preserved where given) |
| `DELETE /menus/{id}` | deletes the menu; rendered media items are left in the library |
| `POST /menus/{id}/render` | 202 `{ job_id }`; progress via `GET /menus/{id}/renders` (`status` per board) |
| `GET /menus/{id}/renders` | current boards with `media_id`, `url`, `language`, `aspect`, `kind`, `status` |
| `POST /menus/{id}/playlist` | creates/updates the draft playlist; returns it |
| `GET /menus/templates` | ids, names, aspects, thumbnail URLs |

Every write is audited with the existing `audit()` helper (`menu.import`, `menu.update`,
`menu.render`, `menu.playlist`). Rate limits follow the existing `slowapi` pattern:
`POST /menus/import` is limited to 5/min per org on top of the monthly quota.

**MCP tools** (Plan B): `menus_import`, `menus_get`, `menus_update`, `menus_render`,
registered in `backend/mcp_server.py` beside the existing 23.

## 8. Dashboard

A new **Menus** section under Content in the sidebar (`data-section="menus"`, all strings
via new keys in `frontend/i18n/en.json` and `ar.json`; `scripts/check_ui_contract.sh`
must pass).

1. **Menus list** — cards with name, item count, template, last rendered; buttons
   **Import with AI** and **New blank menu**; a quota pill ("3 of 5 AI imports left this
   month"). Hidden entirely when `/ai/capabilities.menu_import` is false.
2. **Import modal** — tabs *Website URL* / *Upload PDF or photos* (reuses the media
   picker for already-uploaded files and the dropzone for new ones). After submit, a
   three-step progress view (Fetching → Reading → Drafting) polled every 2 s, with the
   friendly error and a "Try an upload instead" shortcut on failure.
3. **Menu editor** — brand strip (name EN/AR, tagline, colour swatches with a native
   colour input, logo picker), categories as collapsible groups, an item table with
   EN and AR columns side by side, price, note, badges, availability toggle, drag to
   reorder; template picker with tinted thumbnails; **Save** and **Render boards**.
4. **Renders** — grid of current boards with language/aspect chips, per-board
   download, **Create playlist** / **Open playlist**, and a "boards out of date" notice
   when the menu changed after the last render.

RTL: the editor is fully mirrored via logical properties; the AR column is `dir="rtl"`
even in the English UI.

## 9. Gating and cost

Monthly AI-import quota by tier, enforced server-side beside the existing `PLAN_*`
constants and counted from `menu_imports` in the current calendar month excluding
`failed` rows:

| Subscription | Imports / month |
|---|---|
| `trialing` | 1 |
| `starter` | 3 |
| `growth` | 5 |
| `business` | 10 |
| `pro` | 25 |

`trial_expired` and `lapsed` are already blocked by `require_active_subscription`.
Estimated Anthropic cost per import on `claude-opus-5`: roughly 15–25 k input tokens
(page text, one screenshot, up to eight images) and 2–4 k output, ≈ $0.15–0.25.
The frozen system prompt is placed first so it caches across imports.

Operator configuration (`.env`): `ANTHROPIC_API_KEY`, `RENDERER_URL`
(`http://renderer:8080`), `RENDERER_TOKEN`, `AI_IMPORT_MODEL` (default `claude-opus-5`).

## 10. Security and privacy

- SSRF guard on every outbound fetch, in both backend and renderer (§4, §6.1).
- Customer content sent to Anthropic is limited to the page text, screenshot and menu
  images for that import; nothing from other orgs, no credentials, no session data.
- Uploaded menu photos already live in the org's media library under existing access
  rules; rasterised PDF pages go to `UPLOAD_DIR/pdf_pages/<media_id>/` as today.
- The renderer only ever receives HTML generated by our templates from our own data, or a
  URL the user typed; it has no access to the database or the uploads volume.
- Logo downloads are size- and type-checked and stored as ordinary media.

## 11. Testing

Backend (`pytest`, existing fixtures):
- SSRF guard: private ranges, redirects into private ranges, scheme rejection.
- Quota: per-state limits, calendar-month rollover, failed imports not counted.
- Menu CRUD: validation, org isolation, full-tree `PUT` preserving ids.
- Extraction: `extract_menu(inputs, client)` takes the Anthropic client as a parameter; tests
  inject a fake returning fixture `MenuExtraction` objects, plus rate-limit and refusal
  paths.
- Render pipeline: renderer mocked with `respx`; asserts media rows, `render_hash`
  skipping, playlist contents and ordering.
- Import state machine: happy path, fetch failure, interrupted-on-restart.

Renderer: a smoke test that renders a fixture board and asserts PNG dimensions and that
Arabic glyphs are present (compare against a stored reference at a coarse threshold).

Manual: full browser smoke in the test environment — URL import, PDF import, edit,
render EN+AR, create playlist, assign to a zone, see it on a player — in both UI
languages. Before launch, an extraction eval of 5–10 real Kuwait menus (web and PDF)
scored on item count, price accuracy and Arabic quality.

## 12. Rollout

**Plan A — Menus core** (usable without AI): schema, templates, renderer service,
menu CRUD + editor, render → media → playlist, `GET /ai/capabilities` returning
`menu_import: false`. Ships as its own PR; no landing-page changes.

**Plan B — AI import**: fetch/screenshot/PDF inputs, extraction, quota, import UI, MCP
tools, evals. Ships as its own PR. Only when B is deployed does the landing page copy flip:
`features.ai.pill` "Coming soon" is removed, `spotlight.pill` becomes "Now available",
`spotlight.body` drops the Instagram promise, and the CTA links to the dashboard —
per the marketing rule that the AI menu is never described as available before it ships.

Both plans branch from `main` after the UI overhaul lands, since the dashboard section
depends on the new sidebar. Feature flag: the whole section is hidden unless
`/ai/capabilities` allows it, so partially configured environments degrade gracefully.
